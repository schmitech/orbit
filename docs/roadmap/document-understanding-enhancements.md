# Document Understanding Enhancements — Roadmap

Tracks three items from the [File Adapter Guide](../adapters/file-adapter-guide.md#future-enhancements) Future Enhancements list that are now cheaper to build than when that list was written, because supporting infrastructure has landed since: **table extraction from PDFs**, **table-aware chunking**, and **citation/source tracking**. They're grouped here because they're interdependent — table extraction produces the table boundaries that table-aware chunking needs, and both produce the positional metadata that citation tracking surfaces.

## Why now

- **Docling supports table structure extraction, but this pipeline hasn't wired it up.** `server/services/file_processing/docling_processor.py` builds a `{'do_table_structure': True, ...}` dict in `get_converter_config()`, but it's never passed to `DocumentConverter()` — it's dead code today (see Phase 1.1). The capability exists in the library ORBIT already depends on; it just isn't turned on.
- **The chunker plugin architecture already supports structure-aware splitting.** `server/services/file_processing/chunking/` has `FixedSizeChunker`, `TokenChunker`, `SemanticChunker`, `RecursiveChunker`, and `MarkdownHeaderChunker` (splits on markdown headers before falling back to paragraphs/sentences/words). [`chunking-strategies.md`](chunking/chunking-strategies.md) tracks this space in detail and explicitly lists table-aware chunking as unimplemented — a `TableAwareChunker` fits the same interface `MarkdownHeaderChunker` already demonstrates.
- **No source-location metadata exists yet.** A repo-wide search found no `page_number`, `chunk_index`, or `source_location` fields anywhere in `file_chunks` or chunk metadata. Citation tracking requires adding this, and Docling's page-level data is the natural source for it.
- **Reranking is a safe pass-through.** `DocumentRerankingStep._apply_reranking_results()` (`server/inference/pipeline/steps/document_reranking.py`) copies the original doc dict and only adds `relevance`/`reranked` fields — any source-location metadata added to a chunk survives reranking unchanged, so citation tracking doesn't need any reranking-step changes.

## 1. Table extraction from PDFs

**Current state:** `DoclingProcessor` (`server/services/file_processing/docling_processor.py`) parses each file **twice** — once in `extract_text()` (135-192) and once in `extract_metadata()` (194-247) — and in both cases only reads `doc.export_to_markdown()` (177). `get_converter_config()` (249-263) builds a `{'do_table_structure': True, ...}` dict but it is **never passed to `DocumentConverter()`** (`_ensure_initialized()`, line 88 calls `DocumentConverter()` with no args) — it's dead code. Table objects, cell/row/col structure, and bounding boxes on `result.document` are discarded; a table just shows up as an inline markdown table inside the flattened text blob that chunkers later operate on.

### Phase 1.1 — Wire up `do_table_structure` and capture structured tables
- In `_ensure_initialized()`, pass `get_converter_config()`'s output into `DocumentConverter(...)` (check the installed Docling version's constructor/pipeline-options API — recent Docling versions take a `PdfPipelineOptions`/`PipelineOptions` object rather than a plain dict, so this likely needs a small adapter, not a literal dict pass-through).
- In `extract_text()`, after `result = self._converter.convert(temp_path)`, read `result.document.tables` (or the equivalent attribute for the installed Docling version) in addition to `doc.export_to_markdown()`. For each table, capture: table index, page number (if Docling associates one), and row/column cell data.
- Verify: process a PDF with at least one multi-page table and assert (in a new unit test under `server/tests/`) that extracted table objects are non-empty and row/column counts match the source document.

### Phase 1.2 — Persist table structure into chunk metadata
- Decide where table chunks are created: either (a) a dedicated `_extract_tables_as_chunks()` step added to the file-processing pipeline in `file_processing_service.py` that runs alongside/after normal chunking, or (b) have the chunker itself detect and tag table regions (see §3 below, which this phase depends on only loosely — a minimal version can hard-code "one chunk per Docling table" here and let §3 replace it later with finer-grained splitting).
- **Avoid duplicating the table in both plain text and structured metadata.** If a table chunk is emitted as its own `Chunk` (option a/b above), the normal prose chunker must *not* also emit the same table rows as part of a flattened-text chunk — otherwise the same table content gets embedded and returned twice (once as prose, once as structured). The simplest approach: before/during normal chunking, strip the markdown table block that Docling's table-structure output corresponds to out of the text handed to the prose chunker, and only let it flow through the dedicated table-chunk path. Define this exclusion explicitly in the implementation, with a test asserting a table's cell text appears in exactly one indexed chunk per table, not two.
- **Define a storage contract for structured cell data — and this requires an explicit code change, not just a data-shape decision.** Today, a single `chunk.metadata` dict is written verbatim to *both* destinations from the same originating `Chunk` object:
  - Into vector-store metadata: `file_retriever.py` builds `metadata.append({'file_id': ..., 'chunk_index': ..., **chunk.metadata})` (around line 627) before `add_vectors(...)`.
  - Into the backend DB: `file_processing_service.py`'s processing loop calls `self.metadata_store.record_chunk(..., metadata=chunk.metadata)` (line ~941), which lands in `file_chunks.chunk_metadata`.

  Because both call sites currently read the *same* `chunk.metadata` dict, simply "deciding" to keep the full cell grid DB-only has no effect unless the two call sites are made to pass different payloads. Concretely: give `Chunk` (or the table-producing code path) two metadata views — a small vector-store-safe dict (`content_type`, `table_index`, `row_count`, `column_count`, `page_number`/`page_range` — flat scalars only) and a separate, larger DB-only payload (the full cell grid) that is passed to `record_chunk()` but *excluded* from the dict spread into vector-store `metadata.append(...)`. This also sidesteps the vector-backend constraint risk (flat scalars are safe everywhere; nested JSON cell grids are not guaranteed to be accepted by every configured backend).
  - `file_chunks.chunk_metadata` itself is a free-form JSON-serialized `TEXT` column (`sqlite_service.py:320-331`), so no schema migration is needed for the DB-only payload — new keys just go into the existing JSON blob. Check `postgres_service.py` has the equivalent `file_chunks` definition and confirm it also stores `chunk_metadata` as free-form JSON/text before assuming parity.
- Verify: upload a PDF with a table, `POST /api/files/{file_id}/query` (note: the query route is `POST`, not `GET` — see `file_routes.py:654`), and confirm `results[].file_metadata.chunk_metadata.content_type` equals `"table"` with the expected row/column data present exactly once, including when the file was uploaded with encryption enabled. The response path is: `metadata_store.get_chunk_info(chunk_id)` (`server/services/file_metadata/metadata_store.py:393-418`) returns the full DB row — which itself has a `chunk_metadata` field holding our JSON blob — and `file_retriever.py:427-429` assigns that whole row to `result['chunk_metadata']`. Then `_format_results()` (`file_retriever.py:487-493`) sets `formatted_item['file_metadata'] = dict(result['chunk_metadata'])`, i.e. `file_metadata` is the whole DB row, so our fields live one level deeper at `file_metadata['chunk_metadata']['content_type']` (decrypted in place at lines 489-492 when `encrypted` is set) — **not** `file_metadata.content_type` directly. Also confirm no other chunk's `content` duplicates that table's text.

### Phase 1.3 — Query-time table rendering
- Extend `TableRenderer`/`ResponseFormatter.format_table_data()` (`server/retrievers/implementations/intent/domain/response/`) to accept table chunk data from the file pipeline, or add a thin adapter in `file_retriever.py` that converts a table chunk's stored cell data into the `(columns, rows)` shape `TableRenderer.render()` expects. Note these are currently **only** called from the intent-SQL/HTTP/GraphQL pipeline (`intent_sql_base.py:923`, `intent_http_base.py:900`, `intent_graphql_retriever.py:524`, `generator.py:76/93`) — there is no existing call site in `file_retriever.py`, so this is new wiring, not a parameter tweak to an existing call.
- Verify: query a table-containing file and confirm the response renders the table in at least one of the existing formats (markdown table is the most useful for chat display).

**Scope:** Vector-store path only (PDF/DOCX/PPTX/XLSX via Docling). The existing DuckDB path for CSV/Parquet is unaffected since it already handles structured tabular data natively.

## 2. Citation and source tracking

**Current state:** `uploaded_files` captures `page_count` only inside the in-memory metadata dict from `extract_metadata()` (`docling_processor.py:233`) — there's no `page_count` column in the `uploaded_files` table (`sqlite_service.py:299-319`) unless it's folded into the existing `metadata_json` TEXT column. `file_chunks` (`sqlite_service.py:320-331`) has no page/offset columns either. `file_retriever.py._format_results()` (451-497) builds two separate dicts per result: a top-level `metadata` dict (`chunk_id`, `file_id`, `chunk_index`, `confidence`, sourced from `vector_metadata` — i.e. the flat, vector-store-safe payload) and, when present, `file_metadata` (the full DB chunk row fetched via `metadata_store.get_chunk_info()`, whose own `chunk_metadata` field nests our JSON blob — see Phase 1.2's verify step for the exact path). New page fields can go into either, depending on whether they're part of the lightweight vector-store payload or the DB-only payload decided in Phase 1.2.

### Phase 2.1 — Capture page attribution at extraction time
- Depends on Phase 1.1's Docling wiring, since per-element page numbers come from the same `result.document` object that table structure comes from. For non-table text chunks, Docling's markdown/text elements may carry page metadata too (check the actual `result.document` API for the installed version — e.g., `TextItem.prov[].page_no` or similar provenance fields) — capture this per element before it's flattened into the single markdown string.
- **Only use provenance Docling actually reports; never guess.** If per-element page numbers aren't available from Docling for a given format (or for non-Docling processors like `PDFProcessor`/pypdf, which don't produce page-attributed text at all today), do **not** fall back to proportional character-offset estimation against `page_count` — on a document with uneven page density (e.g., a title page, a dense appendix, embedded images), a proportional guess can confidently point to the wrong page, which is worse than no citation at all. Instead:
  - Store an explicit `page_number: null` (surfaced as "page unknown" in the response) when provenance can't be established for a chunk.
  - If Docling exposes page-break markers in the exported text (even without full per-element provenance), use those as a hard boundary signal instead of a proportional estimate — a real boundary, even if coarse, is still a true fact rather than a guess.

### Phase 2.2 — Attach page/offset metadata to chunks
- When the chunker (any strategy) creates a `Chunk`, stamp `chunk.metadata['page_number']` (or `null` per Phase 2.1's rule) using the mapping from Phase 2.1.
- **Define the representation for chunks spanning multiple pages.** Because chunk boundaries (from any chunker strategy) don't necessarily align with page boundaries, a single chunk's text can cross a page break. Represent this as `page_number: null` plus an explicit `page_range: [start, end]` field when a chunk is known to span pages `start` through `end` (from Docling's per-element provenance); reserve plain `page_number: <n>` for chunks confirmed to lie entirely within one page. Consumers (Phase 2.3's response and any UI) should treat `page_range` as "spans pages N–M" and `page_number: null` with no `page_range` as "page unknown" — these are two distinct, explicit states, not a silent fallback to either.
- This likely means passing page-attribution data through `file_processing_service.py`'s call into the chunker (`chunk_text(text, file_id, metadata)` — the `metadata` param already exists on the abstract method signature in `base_chunker.py:101-113`, so this is passing more through an existing parameter, not adding one).
- No `file_chunks` schema migration needed if stored inside the existing `chunk_metadata` JSON column; add a real column only if the field needs to be SQL-queryable/indexable later.

### Phase 2.3 — Surface citations in the query response
- In `file_retriever.py._format_results()` (451-497), add `page_number` into the per-chunk `metadata` dict (alongside `chunk_id`/`chunk_index`/`confidence`, lines ~479-483) when present in `vector_metadata`/`chunk_metadata`. No changes needed in `file_routes.py`'s `query_file()` (654-766) since it passes `results` through from the retriever largely unmodified (its only mutation today is adding `metadata['file_id']` at lines 752-754).
- Confirm reranking doesn't need changes: `DocumentRerankingStep._apply_reranking_results()` (`server/inference/pipeline/steps/document_reranking.py:318-345`) copies the original doc dict and only adds `relevance`/`reranked` — any `page_number` already on the dict survives untouched.
- Verify: query a multi-page PDF and confirm each result's `metadata.page_number` matches manual inspection of the source file.

**Dependency:** Phase 2.1 builds directly on Phase 1.1 (Docling wiring) for documents that mix prose and tables, since Docling returns page attribution for both element types as part of the same parse.

## 3. Table-aware chunking

**Current state:** No chunker in `server/services/file_processing/chunking/` is aware of table boundaries. `TextChunker` (`base_chunker.py:41-118`) is the abstract base (`chunk_text(self, text, file_id, metadata) -> list[Chunk]`, lines 101-113); `MarkdownHeaderChunker` (`markdown_header_chunker.py`, 89 lines) is the closest existing analog — it subclasses `RecursiveChunker`, configures a header-regex split rule ahead of paragraph/sentence/word fallback rules, then post-processes chunks to stamp `metadata['strategy']`/`header_level`/`section_header`. `file_processing_service.py._init_chunker()` (260-347) dispatches on `chunking_strategy` via an if/elif chain (`'semantic'` 281-312, `'token'` 314-322, `'recursive'` 323-332, `'markdown_header'` 333-342, else fixed-size).

### Phase 3.1 — Detect table boundaries in text
- Depends on Phase 1.2's table metadata existing (table index/boundaries identified by Docling). For the markdown-flattened text Docling already produces, table boundaries can also be detected directly via regex on markdown table syntax (`|...|` rows with a `---|---` separator line) as a fallback/independent signal, which is useful even before Phase 1 lands and gives this item partial independence from §1.
- Add a `TableAwareChunker` class in `server/services/file_processing/chunking/table_aware_chunker.py`, following `MarkdownHeaderChunker`'s shape: either subclass `RecursiveChunker` with a custom `RecursiveRules` level that treats a detected table block as an atomic, unsplittable unit, or wrap an existing chunker and post-process its output to merge/re-split chunks so no chunk boundary falls inside a detected table.

### Phase 3.2 — Preserve whole tables as chunks
- When a table region is detected, emit it as one chunk (or one chunk per logical row-group for very large tables exceeding `chunk_size`), stamping `chunk.metadata['content_type'] = 'table'` (same marker as Phase 1.2, so downstream rendering in §1.3 works regardless of which stage produced the marker) plus `table_index` to correlate with Phase 1's structured table data if both are enabled.
- Surrounding prose falls through to the wrapped chunker's normal paragraph/sentence/word splitting — no change to that behavior.
- **A "whole table chunk" from the chunker is not guaranteed to survive as one chunk all the way to the vector store.** `FileVectorRetriever.index_file_chunks()` (`server/retrievers/implementations/file/file_retriever.py:499-`, splitting logic at `529-554`) re-validates every chunk's text against the embedding model's token budget immediately before embedding, and calls `split_text_to_budget()` to break any chunk that doesn't fit — this runs *after* chunking, so a table chunk this phase marks as atomic can still be split again at indexing time if it exceeds the embedding budget. Define what happens in that case:
  - `split_text_to_budget()` splits on plain text, not on table structure — it has no notion of rows/columns, so a naive split can still break mid-row even though this phase's chunker kept the table whole.
  - The indexing-time split path already copies `dict(chunk.metadata)` onto each resulting piece (`file_retriever.py:554`) and adds `parent_chunk_id`/`split_index`/`split_count` — so `content_type: 'table'`, `table_index`, and any `page_number`/`page_range` from Phase 2 *do* survive onto split pieces automatically, but the identical structured cell-grid JSON from Phase 1.2 (if stored in metadata) would then be duplicated verbatim across every split piece, which is misleading (each piece would claim to "contain" the full table while only holding a text fragment of it).
  - Required fix: either (a) give `index_file_chunks()` a table-aware split path — when a chunk has `content_type: 'table'` and must be split, split on row boundaries (one or more whole rows per piece) instead of calling the generic `split_text_to_budget()`, and update each piece's metadata to a `row_range` subset of the original table rather than copying the full cell grid unchanged; or (b) for oversized tables, don't rely on the chunker to keep them atomic at all — emit them pre-split by row-group in Phase 3.1/3.2 at a size that's already within the embedding budget, so the generic indexing-time split never triggers for table chunks. Pick one in a design review before implementing, since they imply different work in `table_aware_chunker.py` vs. `file_retriever.py`.
  - **Split pieces get new chunk IDs that the DB never learns about — this must be reconciled, independent of which option above is chosen.** `index_file_chunks()` only returns `bool` (`file_retriever.py:499`, `return True`/`return False`); the caller in `file_processing_service.py`'s processing loop (`~900-946`) persists chunk records via `self.metadata_store.record_chunk(...)` in a `for chunk in chunks:` loop over the **original, pre-split** `chunks` list (the output of `_chunk_content()`, before `index_file_chunks()` ever runs). When `index_file_chunks()` internally splits a chunk, it mints new ids like `f"{orig_id}_split_{sub_i}"` (`file_retriever.py:553`) and writes *those* ids into the vector store — but `record_chunk()` never runs for them, so `file_chunks` in the backend DB has no row for a split piece's chunk_id. At query time, `metadata_store.get_chunk_info(chunk_id)` (`metadata_store.py:393-418`) looks up `file_chunks` by exactly that chunk_id and returns `None` for any split-piece id with no row — so a retrieved split-piece chunk would have no `file_metadata` at all, losing both its table/row attribution (Phase 1) and its page citation (Phase 2).
  - Required fix: change `index_file_chunks()` to return the final, post-split list of `Chunk` objects actually written to the vector store, not just a `bool`. But this return value must pass through an intermediate layer too: `file_processing_service._index_chunks_in_vector_store()` (`file_processing_service.py:1554-1561`, `-> tuple | None`) is the only caller of `index_file_chunks()` and today returns just `(collection_name, embedding_provider, embedding_dimensions)` on success — it must also be changed to return (or otherwise propagate) the final chunk list it gets back, since the processing loop that calls `record_chunk()` only has access to `_index_chunks_in_vector_store()`'s return value, not `index_file_chunks()`'s directly. This is a signature change to **both** functions and all of their call sites — `index_file_chunks()`'s caller at `_index_chunks_in_vector_store()`, and `_index_chunks_in_vector_store()`'s two callers (`file_processing_service.py:927` and `:1181`) — so audit all of them before implementing.
  - **Encrypted files break this further: metadata encryption currently happens before splitting, bound to the wrong id.** When `requires_encryption` is set, `_encrypt_chunk_metadata()` (`file_processing_service.py:768-796`) runs on the **pre-split** `chunks` list (called at `file_processing_service.py:924` and `:1178`, both *before* `_index_chunks_in_vector_store()`/`index_file_chunks()` run) and replaces `chunk.metadata` in place with `{'encrypted': True, 'payload': <hex>}`, where the ciphertext's AAD is bound to that chunk's **original** `chunk_id` (`aad = chunk.chunk_id.encode('utf-8')`, line 794). If `index_file_chunks()` later splits that chunk, the sub-chunk copies this already-encrypted envelope unchanged (`dict(chunk.metadata)`, `file_retriever.py:554`) but is assigned a **new** `chunk_id` (`{orig_id}_split_{sub_i}`). At query time, decryption uses the split piece's own id as AAD (`file_retriever.py:470`, `:491`, `aad = chunk_id.encode('utf-8')` where `chunk_id = result.get('id')`) — an AES-GCM AAD mismatch against the ciphertext's original-id AAD, so decryption of that split piece's metadata envelope will fail (an authentication-tag error), not silently return wrong data.
  - Required fix: re-key (re-encrypt) each split piece's metadata envelope with its own final `chunk_id` as AAD, and this must happen *after* split ids are finalized, not before. Chunk **text** encryption already gets this right today — `index_file_chunks()` encrypts `chunk_texts` using the finalized `ids` list only after splitting is done (`file_retriever.py:618-624`), and it already receives an `encryptor` parameter for that purpose. The metadata envelope should follow the same pattern: move `_encrypt_chunk_metadata()`'s logic out of `file_processing_service.py`'s pre-split call sites and into `index_file_chunks()` itself, applied to `validated_chunks` (the post-split, id-finalized list, `file_retriever.py:576-593`) immediately before those chunks are persisted — reusing the `encryptor` parameter `index_file_chunks()` already accepts, so no new parameter is needed, just relocated logic.
  - Verify: construct a table large enough to exceed the configured embedding budget, confirm it is still split cleanly at row boundaries (no row's cells divided across two chunks), confirm every resulting piece retains correct `table_index` and `page_number`/`page_range` attribution, confirm `metadata_store.get_chunk_info()` called directly on each split piece's chunk_id returns a non-`None` row, and — with `files.encryption.enabled: true` and an adapter marked `requires_encryption: true` — confirm each split piece's metadata envelope decrypts successfully via `POST /api/files/{file_id}/query` rather than raising an AAD/authentication error.

### Phase 3.3 — Wire into the chunker dispatch
- Add a `'table_aware'` branch in `_init_chunker()` (`file_processing_service.py`, alongside the existing `'markdown_header'` branch at 333-342), reading any table-specific knobs from `chunking_options` (line 276).
- Document the new `chunking_strategy: "table_aware"` option in `docs/adapters/file-adapter-guide.md`'s Chunking Strategies section once implemented.
- Verify: upload a document containing a large table that would normally straddle a `FixedSizeChunker`/`SemanticChunker` boundary; confirm with `table_aware` strategy enabled the table arrives as a single chunk (or clean row-group chunks) with no row split across chunk boundaries.

**Dependency:** Table boundary detection can proceed independently via markdown regex (see Phase 3.1), but full fidelity (true cell/row/column structure rather than markdown-text-shape detection) requires Phase 1.1/1.2's Docling table objects.

## Suggested phasing

1. **Phase 1.1 → 1.2** (Table extraction, wiring + persistence) — unlocks accurate signals for both items below; no schema migration required, only new keys in the existing `chunk_metadata` JSON blob.
2. **Phase 2.1 → 2.3** (Citation tracking) — highest standalone user-visible value (answers can finally cite a page); can start once Phase 1.1 lands since it reuses the same Docling parse.
3. **Phase 1.3** (Table rendering) and **Phase 3.1 → 3.3** (Table-aware chunking) — lower urgency, can proceed in parallel once Phase 1.2's table metadata format is settled; Phase 3's boundary detection can start even earlier via the markdown-regex fallback if prioritized sooner.

## Non-goals (not included in this roadmap)

The following Future Enhancements items have no recent supporting work and are deliberately excluded here:

- Multi-document analysis
- Streaming processing for large files
- Document versioning and history
- Chart understanding (bar charts, line plots, etc.)
- Chemistry structure understanding
